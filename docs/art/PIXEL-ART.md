# Pixel pond and ducks (gate 6)

All art is **original, generated deterministically in code** by `src/QuotaDuck.Art` (pure BCL: no WPF, no System.Drawing, no I/O, no clock,
no randomness). There are no image files except one generated `.ico`. Nothing is copied from or modelled on TokenFish.

## Metaphor
Remaining quota = remaining water. As usage rises the pond's water level falls, its bowl narrows (it is an ellipse), the wet shore and stones
appear, and the duck stops floating and stands. **Exact numbers are always printed beside the art** (percent used / left, reset countdown,
age, state word); the picture never replaces them and is never needed to understand a state.

The `.ico` is regenerated by `tools/QuotaDuck.AssetGen` (`dotnet run --project tools/QuotaDuck.AssetGen -- <repo> [--previews <dir>]`); a test
asserts the embedded resource equals the generator's output byte for byte. It is **not** rendered through WPF (that pulled Direct3D and the GPU
driver into the tray-only process: +14 MB private, +22 MB working set).

## Pond-state mapping (`PondMapping`, pure)
| Provider state | Pond | Duck |
|---|---|---|
| Fresh/Quiet, water >= 6 rows (>= ~37% left) | real level, normal colours | awake, floating |
| Fresh/Quiet, shallow (< 6 rows) | real level, more shore, stones and wall reeds visible | awake, standing on the bottom |
| 100% used | a one-row, 13 px puddle | standing |
| Sleeping (data hours old) | last known level, **subdued** colours | sleeping (closed eye, bobbing `z`), floating or standing |
| Window elapsed, no number | full bowl of **hatched** water (diagonal stripes) — never solid, never 100% | hollow outline duck with `?` |
| No data / waiting / provider off | dry hatched bowl | hollow outline duck with `?` |
| Failure and no data | dry hatched bowl | standing duck with a red `!` |
| Failure but older data exists | the last known pond | its normal duck plus a red `!` beside it |
| Codex reading | unchanged | `..`/`...` dots beside the duck |

The pond shows the **tightest numeric window** of the provider (highest used %); each window also has its own gauge. Windows are mapped
independently (one elapsed window never hides the other's number). Claude's duck faces right, Codex's left; their states are independent.

## Animation (sparse, visible-only, never required)
* 2-frame water ripple, bobbing `z`, busy dots: the frame flips on the existing 1 Hz tick that only runs **while the flyout is visible**.
* Refill: when a pond's water rises by >= 25 points (e.g. an elapsed window reports a new level) the level rises over 8 steps of 80 ms on a
  short-lived ticker (`PondAnimator`), stopped when done or when the flyout hides.
* **Reduced motion** (Windows "Show animations" off, re-read every time the flyout opens): frame fixed at 0, no refill. **Hidden: nothing runs.**

## Rendering
`PixelImage` turns an `ArtScene` into a frozen `WriteableBitmap`: palette -> BGRA at an **integer scale** chosen from the window DPI
(`PixelScale.Choose`; every art pixel is a k x k block of device pixels, shown 1:1, nearest-neighbour, aliased edges), cached by
(scene, scale, high-contrast, dpi). High Contrast swaps in the 4-colour system palette.

## Accessibility
Each pond has an automation name that spells out level, window and duck ("Claude pond: 58 percent of the water is left in the tightest window
(5-hour); the duck is swimming."); gauges are decorative (hidden from assistive technology; the row text carries the numbers); state is always
also a word ("Fresh", "Sleeping (old)", "Reset", "No data"); keyboard/Esc/Tab behaviour unchanged; colours are decoration only.

## Window lifetime decision
Measured destroy-on-hide vs keep-alive (synthetic data, 4 open/hide cycles): destroy-on-hide saves ~5 MB private / ~4 MB working set and makes
re-open ~100 ms instead of ~30 ms. The rule asked for >= ~25 MB; **keep the window alive**.
